# Booting an image

How memory gets filled and where execution starts: ELF loading, boot tables and configuration
tables, HPI host boot, I2C EEPROM boot, and Ethernet and UTOPIA boot with external hosts.

`--boot-mode` is the BOOTMODE pins. Mode 0 starts every core at once. Mode 1 is hardware HPI
boot: all cores wait in reset for the external host, with no ROM involved. C6455 mode 5 (I2C)
and C6472 modes 5-8 (UTOPIA) and 9-10 (Ethernet) hand the boot to the ROM model, which runs
*in place of* core 0 while core 0 is held. Other modes run core 0 and leave it to release the rest.

A note that applies to these ROM modes: the ROM's own instructions are not modelled. TI ships
them in on-chip ROM this project has no copy of, and SPRUEC6G warns that their addresses change
between silicon revisions. The models reproduce the boot transport, memory writes, core release
and peripheral setup described below, not instruction-level ROM execution or its transient
CPU register/interrupt-handler state.

A core held in reset, by any of these boots or by the C6472's boot controller, receives no
interrupts: an event raised while it waits never reaches its IFR. The interrupt controller still
latches the event in EVTFLAG.

## The default: ELF segments

`c64xemu run IMAGE` loads the ELF's `PT_LOAD` segments into the backing store and starts at the
ELF entry point. This is the path every target program and both firmware images use, and it is
the only mode in which the ELF's *contents* place anything in memory.

`src/elf.rs` accepts ELF32 only, requires the machine type to be `EM_TI_C6000`, and refuses a
segment whose file size exceeds its memory size. **Endianness is not an option** — it is read
from `e_ident[5]` and becomes the device's, which is what strapping LENDIAN would do on a board.
A big-endian image therefore just runs; `tests/programs/big_endian` and `big_endian_rts` are the
cases that hold that down, and the byte order also decides how boot-table words are read and how
three peripherals report their registers.

Symbols are read in every mode, because `--break`, `--stop-pc` and the debugger resolve names
through them.

## Boot tables

A boot table is the format the ROM bootloader loads memory from, whether it sits in memory or
arrives over a link. `src/boot.rs` implements [SPRUEC6G](../reference/spruec6g.pdf) §6.2.2 and
§6.2.3 exactly:

```
u32   entry point
repeat:
  u32 byte count        (zero terminates the table)
  u32 destination address
  ...   `count` bytes of data
u32   0                 terminator
```

A table already in memory is read word by word in the device's byte order, which is what the
hex conversion utility's `-order` option matches to the build. A table that arrives over I2C
or UTOPIA carries its words most significant byte first instead (see below).

`--boot-table FILE:ADDR` places the file at `ADDR` and loads memory from it instead of from the
ELF segments; the ELF then supplies only symbols. The destination of a section is any address a
CPU access reaches — which is the whole trick behind multicore boot, because writing
DSP_BOOT_ADDRn and BOOT_COMPLETE_STAT is a section like any other. See
[The six-core device](multicore.md).

## Boot configuration tables

A boot configuration table is a list of three-word entries applied before the boot table:

```
repeat:
  u32 address
  u32 set mask
  u32 clear mask
end: three zero words
```

The bootloader reads the address, sets the bits in the set mask, clears the bits in the clear
mask, and toggles the bits that appear in **both**. An entry whose two masks are zero names a
function the bootloader calls with the return address in B3; `src/boot.rs` reports those
addresses to its caller rather than branching itself. The table ends when all three words are
zero.

`--boot-config FILE:ADDR` applies one. It is how a real board programs a memory controller or a
PLL before the image lands.

## HPI host boot

### C6455 host boot

`--boot-mode 1 --hpi-unix PATH` on the C6455 is host boot through the HPI. SPRS276M section 2.4
calls it a hardware boot mode: "the CPU is actually held in reset until a DSP interrupt is
generated by the host". The ELF loads nothing; the host writes code and data straight into
memory over the [HPI host side](networking-and-host-io.md#the-hpi-host-side). There is no boot
table and no entry record.

The boot mode is a reset strap, so its effects are in place before the first cycle:

- PERCFG0.HPICTL reads 1 and PERSTAT0 reports the HPI enabled (SPRS276M Table 3-7: HPICTL
  "defaults to 1 when host boot is used").
- HPIC.HPIRST reads 0 (SPRU969B Figure 31), so the host can reach memory before any code runs.
- L1P and L1D are 32 KB of cache and L2 is all SRAM (SPRUEC6G Table 2).
- Core 0 is held in reset with its PC at `0x00800000`.

The first DSPINT the host raises takes core 0 out of reset. It starts at the base of L2,
`0x00800000`, whatever the ELF's entry point says, so link the image there. It starts with reset
CPU state: GIE is clear and ISTP is at its default. DSPINT itself stays set: "the CPU needs to
clear the DSPINT, otherwise, no more DSPINTs can be received". Every DSPINT after the first is an
ordinary interrupt for the application (system event 15). The one that ended the boot arrived
while the core was in reset, so it is not pending in IFR.

On the C6455 every DSPINT also raises EDMA3 event DSP_EVT (channel 0), including the interrupt
ending boot (SPRS276M section 7.4.1). Firmware must clear ER bit 0 before enabling channel 0
if it does not want that pending boot event to initiate a transfer.

The host does not have to be a process. `--hpi-replay FILE` boots from a
[timed file of host accesses](networking-and-host-io.md#replaying-the-host-from-a-file), which
makes an HPI boot an ordinary batch run. The smallest C6455 boot loads one NOP at the L2 entry,
checks it, and releases the core with DSPINT:

```csv
tick,port,direction,value
0,control,write,0
0,address,write,0x00200000
0,data-auto,write,0x00000000
0,address,write,0x00200000
0,data,read,0x00000000
1,control,write,0x00000002
```

The second HPIA write is the fence that flushes the posted write (SPRU969B section 6.3): a file
that leaves words in the write FIFO leaves them unwritten.

`tests/tools/hpi_host.py --boot --image IMAGE` is a host for the C6455 boot. It writes each
`PT_LOAD` segment, padded with zeros to its memory size, and reads it back to verify it.
It flushes the final partial FIFO burst by rewriting HPIA, then raises DSPINT.
`--no-dspint` stops before release.

### C6472 host boot

With `--device c6472 --boot-mode 1 --hpi-unix PATH`, all six cores are held in reset and
HPIC.HPIRST is clear. Every core has 32 KB L1P and L1D caches and L2 configured as SRAM
(SPRUEC6G section 4.3.2 and Table 21; SPRUEG1B Figure 22). The ELF supplies only symbols.
The host loads code and data through global core-local aliases, writes `DSP_BOOT_ADDRn`
with the entry address shifted right by 10, then sets the selected BCn bits in
`BOOT_COMPLETE_STAT`. Each rising BCn releases that core at its programmed entry.
Unselected cores remain held. DSPINT alone never releases a C6472 core.

On either device allowed HPI accesses reach chip-level peripheral registers and memory;
memory protection judges the HPI as privilege ID 0. The megamodule registers at
`0x0180_0000`-`0x01BF_FFFF` (cache configuration, interrupt controller and memory protection)
are the CPU's alone (SPRU871K section 5.3.1).

The C6455 additionally excludes Device Configuration, including Device State Control
(`0x02A80000`-`0x02AFFFFF`), PLL1 (`0x029A0000`-`0x029BFFFF`) and PLL2
(`0x029C0000`-`0x029CFFFF`) from host access (SPRS276M section 4.3, Table 5-11 and sections
7.7.3/7.8.3). These exclusions apply after boot too. The C6472 permits PLL1/PLL2 and boot-controller
access, but excludes PLL3 at `0x029C0400`-`0x029C07FF` (SPRS612G section 7.10.3).

Forbidden reads return zero and writes are ignored, without holding off the host. For the
host-inaccessible configuration windows the manuals do not specify a read value or response
timing: this is deterministic emulator policy, not behavior firmware should rely on in hardware.
The host filter does not change CPU or IDMA access.

The same boot from a file, for core 0: `0x04200000` is core 0's L2 global alias
`0x10800000 >> 2`, `0x00aac081` is `DSP_BOOT_ADDR0` (`0x02ab0204 >> 2`), `0x2000` is the entry
`0x00800000 >> 10`, and `0x00aac001` is `BOOT_COMPLETE_STAT` (SPRUEC6G section 4.3.2).

```csv
tick,port,direction,value
0,control,write,0
0,address,write,0x04200000
0,data-auto,write,0x00000000
0,address,write,0x04200000
0,data,read,0x00000000
0,address,write,0x00aac081
0,data,write,0x00002000
0,data,read,0x00002000
1,address,write,0x00aac001
1,data,write,0x00000001
```

`tests/tools/hpi_host.py --device c6472 --boot --image IMAGE --cores 0,3 --report`
loads and verifies the image for cores 0 and 3, programs their entries, then releases them
in one write. Omit `--cores` to select all six. Local segments are replicated at each selected
core's global alias; shared segments are written once. Link the entry at a 1 KB boundary
inside the C6472's 608 KB local L2. `--no-release` loads without releasing; adding `--dspint`
demonstrates that DSPINT does not end this boot. `--state-out FILE` records
`hpi_boot.entries`, one entry per core (null while held), and `hpi_boot.entry` for core 0.

`tests/test_hpiboot.py` checks the C6455 in both byte orders and the C6472 with all six cores,
selected subsets, nondefault entries in both byte orders, and no release. Away from the L2 base
the probe links a guard there, so a core started at the default address instead of its
programmed one fails the run. The multicore probe disables L1D before using its shared result
mailbox: the cores' caches are not coherent with one another.

## I2C EEPROM boot

`--boot-mode 5 --i2c-eeprom FILE` is the C6455's master I2C boot of SPRUEC6G Table 3 and §2.3.4:
the way a board with a boot EEPROM comes up. On the C6472 it is `--device c6472 --boot-mode 2`
(EEPROM at 0x50) or `3` (0x51), §4.3.3 and Table 22. The ELF loads nothing.

The read sequence goes through the modelled I2C master's own registers — ICSAR, ICCNT, ICMDR,
ICDXR and ICDRR are driven exactly as firmware drives them, two internal address bytes as a
master transmit, then a repeated START and a master receive — and the EEPROM answers as a
board's would. `src/i2c.rs` therefore models what §2.3.4 requires of the device: two-byte
internal addressing, an auto-incrementing address counter, and the slave address the mode names.

Everything on the EEPROM is blocked, at most 128 bytes per block including a four-byte header:

| Offset | Field |
|---|---|
| 0 | 16-bit block size, counting the header |
| 2 | 16-bit ones-complement checksum over the block, including the size and checksum fields |
| 4 | the block's payload |

Valid checksums are 0 and −0, and a checksum field of 0 disables the check. A failed block is
re-read once.

The boot is two stages. First a boot parameter block: the blocks begin at EEPROM address 0 and
each is 128 bytes, and the DSP picks one by its configuration pins — CFGGP[2:0] on the C6455,
CFG[3:0] on the C6472 — at address `0x80 * index`, which `--boot-param-index N` sets. Its options
field says what follows: 0 another parameter table, 1 a boot table, 2 a boot configuration
table. For a boot table the sections are streamed block by block into memory, and core 0 is
then branched to the entry point. A configuration table's read/modify/write entries (§6.2.3)
are applied as their blocks arrive; the boot then re-enters at the parameter block's next
device address and reads another parameter block there. An entry that asks the ROM to call a
function stops the boot.

Boot-table and configuration-table words travel most significant byte first on both byte
orders: §6.2.2.3.1 builds the table with `hex6x -a`, which writes each 32-bit word that way for
`-order L` as for `-order M`, and TI's IBL `bconvert64x` says "The C6x boot loader expects all
32 bit values to be in big endian". The ROM model reads each word that way and stores it as the
device does, so a little-endian device turns every word's bytes round. Until TI's own tools
were run against it, the model read the words in the device's byte order and the suite's
builders wrote them that way, which agreed with itself and with nothing TI made.
A block need not end on a word: §2.3.4.1 sets only a 128-byte maximum, so the first bytes of a
word a block ends inside are held until the next block of the same table completes it.

### The C6472's differences

| | C6455 | C6472 |
|---|---|---|
| Modes | 5 | 2 (0x50), 3 (0x51) |
| Parameter block index | CFGGP[2:0] | CFG[3:0] |
| PLL1 | untouched | x9, or x19 with `--i2c-pll-x19` (CFG[4]) |
| Caches | untouched | Table 21: 32 KB L1P, 16 KB L1D, no L2 cache |
| Parameter block | Table 6 behind the 4-byte header | Table 25 behind Table 23's 10-byte header |

The C6472 header adds an extended boot mode (Table 24) to every parameter block. 0x101 is the
I2C boot itself and acts on the options as above; 0x104 hands the device to the UTOPIA boot,
configured by the block's Table 26 fields (see [UTOPIA boot](#utopia-boot)). Any other mode
stops the boot. Cores 1-5 stay held until the table releases them.

Boot-table and configuration-table blocks keep the four-byte header: Table 23's header belongs to
the parameter tables. TI's own C6472 tools say so: the ROM's `tiboot_c6472.h` and the C6472 EVM
EEPROM build in TI's IBL (git.ti.com/keystone-rtos/ibl), whose `b2i2c` cuts the boot table into
four-byte-header, 124-byte blocks behind `romparse` parameter tables. The same header masks the
options' table type to bits 1:0 and gives bits 4:2 to the EEPROM type, which the boot ignores.
**[INFERENCE]** The software PLL field is not applied; nothing in the manual gives it an effect
on the C6472.

`tests/tools/i2c_eeprom.py` lays out a C6472 EEPROM from an ELF: the selected parameter block,
then the boot table, or with `--utopia` a UTOPIA parameter block, and with
`--config ADDR,SET,CLEAR` a configuration table in front of the next parameter block. Its layout
is `romparse -compact`'s, and `tests/test_i2cboot.py` holds it to TI's: the IBL's own tools,
fetched by `tests/tools/fetch_deps.sh` and built by `tests/tools/ibl_tools.py` (which needs
`bison` and `flex`), make an EEPROM the emulator must boot and the builder must match byte for
byte.

```console
$ python3 tests/tools/i2c_eeprom.py --image IMAGE.out --out eeprom.bin --index 5 --slave 0x51
$ target/release/c64xemu run IMAGE.out --device c6472 --boot-mode 3 --boot-param-index 5 \
    --i2c-pll-x19 --i2c-eeprom eeprom.bin --state-out /tmp/i2c-state.json
```

### TI's IBL

The EEPROM can also hold what TI's C6472 EVM shipped with: TI's Intermediate Boot Loader, whose
first stage the ROM loads and which then reads the rest of itself off the EEPROM with its own
I2C driver, sets up PLL1 and DDR2, and boots over Ethernet by BOOTP and TFTP.
`tests/tools/ibl_build.py` builds it from TI's source (`make evm_c6472`, one EEPROM per byte
order) into `tests/build/ibl-c6472/`, and `tests/tools/ibl_peer.py` launches the emulator and
serves the BOOTP reply and the file. The IBL loads the file as a binary blob at 0xE0000000 and
branches there, so the program it boots must be linked to start at the base of DDR2;
`tests/test_ibl.py` shows the link and the conversion. The image passed as `--image` names the
device's byte order and the symbols; nothing in it is loaded.

The peer prints one JSON report and exits 0 only when the whole boot worked: the TFTP transfer
completed without an error and the program then halted at its exit with no fault. A program that
merely leaves the right value in A4 when the cycle limit runs out does not count. The program's
own console output is in the state file's `cio_output`.

```console
$ python3 tests/tools/ibl_build.py le
$ python3 tests/tools/ibl_peer.py --emulator target/release/c64xemu --image APP.out \
    --eeprom tests/build/ibl-c6472/le/bin/i2crom_0x50_c6472_le.bin \
    --blob app.bin --file-name app.bin --max-cycles 3000000000 --state-out /tmp/ibl.json
```

## UTOPIA boot

`--device c6472 --boot-mode 5` through `8` selects UTOPIA cold boot
([SPRUEC6G](../reference/spruec6g.pdf) §4.3.4, Tables 22 and 26). Modes 5/6 use an 8-bit bus;
7/8 use a 16-bit bus. The paired modes program PLL1 x10/x20. `--utopia-phy N` sets CFG[4:0]
and the slave address, default 0; it is refused outside this boot, where nothing reads it.
Address 31 is the null PHY and cannot receive a boot. The C6455 has no UTOPIA boot mode; its
mode 5 remains I2C.

Run the emulator and sender in separate terminals:

```console
$ target/release/c64xemu run IMAGE.out --device c6472 --boot-mode 7 \
    --utopia-phy 11 --utopia-unix /tmp/dsp-utopia.sock --max-cycles 100000000 \
    --state-out /tmp/utopia-state.json
$ python3 tests/tools/utopia_boot.py --image IMAGE.out --width 16 --phy 11 \
    --socket /tmp/atm-master.sock --peer /tmp/dsp-utopia.sock --json
```

The ELF supplies only symbols and endianness to the emulator. The sender builds a boot table
from its load segments and sends 32 bytes per cell, followed by the big-endian magic
`54 49 21 64`. The remaining payload bytes are unused; the last table fragment is zero-padded.
Standard wire cells have 5 header bytes in 8-bit mode, 6 in 16-bit mode, and 48 payload bytes.
The sender waits for explicit acceptance and retries refused writes, not unanswered writes.

The table travels as big-endian words - what `hex6x -order M` writes - whatever the device's
byte order. The ROM assembles cells big-endian, so each wire word lands in L1D most
significant byte first, and the boot-table processing reads the payload as it sits in memory:
on a little-endian device that is the word the table meant. **[INFERENCE]** No manual states the
wire order for a little-endian device; this is what the documented BEND setting gives a ROM
that does not swap the bytes back.

The ROM configures core 0 with 32 KB L1P cache, 16 KB L1D cache and no L2 cache. PDMA channel 8
delivers 56-byte packets into the addressable half of L1D, wrapping after 292 cells. Half/full
PDMA interrupts and timer 0 wake the boot processor: 100 µs for 8-bit, 50 µs for 16-bit, using
the documented default 500 MHz core frequency and integer CPU/6 timer counts. It searches
backward for the magic, discards/counts invalid cells, and feeds the preceding 32 bytes to
`BootStream`. Completion disables all receive PDMA channels and timer 0 and branches core 0
to the table's entry - the base of L2, `0x00800000`, when the table names 0, as for every ROM
boot. Other cores remain held unless the table releases them.

`utopia_boot` in the state report records accepted/discarded cells, table bytes, entry and error.
The byte count includes 32 bytes for the final padded cell. A table that never terminates -
more sections than any image, which is the one malformation the stream can recognise - leaves
core 0 held and reports an error. `--boot-table`, `--boot-config` and `--i2c-eeprom` cannot be
combined with this boot source.

### Parameters from an I2C EEPROM

A C6472 I2C boot whose parameter block names extended boot mode 0x104 runs the same UTOPIA boot
with that block's Table 26 fields instead of the cold-boot defaults:

| Offset | Field | Effect | Cold-boot default |
|---|---|---|---|
| 10 bit 0 | single-PHY | clears UCR.MPHY: every address reaches the port | multi-PHY |
| 10 bit 1, 14 | bus width | UCR.U16M; the two must agree and be 8 or 16 | from the mode |
| 10 bit 2 | skip port initialisation | UCR is not written | initialise |
| 12 | physical cell size | UCR.RUDC = size − 53 (8-bit) or − 54 (16-bit), up to 64 bytes | 53 / 54 |
| 16 | slave ID | UCR.SLID | CFG[4:0] |
| 18 | core frequency, MHz | timer 0's period | 500 |

The cell size sets the packet — the cell padded in front to whole words, 14 to 16 of them — and
with it the PDMA burst and the buffer: 16 KB holds 292 standard cells and 256 of 64 bytes, the
"256 to 292 cells" of §4.3.4. The 48-byte payload is always the packet's last twelve words.

**[INFERENCE]** Skipping port initialisation skips the UCR write and nothing else: the PSC, PDMA
channel 8 and timer 0 are how the ROM finds cells at all, so they are still programmed. The port
is left as reset or an earlier configuration table left it. A chained boot does not reprogram
PLL1 or the caches; the I2C boot set both. A table whose fields the port cannot be set up from
stops the boot with core 0 held.

```console
$ python3 tests/tools/i2c_eeprom.py --image IMAGE.out --out eeprom.bin --utopia \
    --width 8 --cell-size 64 --slave-id 9 --core-mhz 250
$ target/release/c64xemu run IMAGE.out --device c6472 --boot-mode 2 --i2c-eeprom eeprom.bin \
    --utopia-unix /tmp/dsp-utopia.sock --state-out /tmp/utopia-state.json
$ python3 tests/tools/utopia_boot.py --image IMAGE.out --width 8 --cell-size 64 --phy 9 \
    --socket /tmp/atm-master.sock --peer /tmp/dsp-utopia.sock --json
```

The ATM master's socket protocol is in
[Networking and host I/O](networking-and-host-io.md#the-utopia-atm-master). The receive PDMA's
peripheral-bus address interpretation and unmodelled transfer modes are listed in
[Peripherals](../internals/peripherals.md#utopia).

## Ethernet boot

`--boot-mode 9` (MAC port 0) or `--boot-mode 10` (port 1) is SPRUEC6G §4.3.5, the way a board
with no boot EEPROM comes up. Nothing at all is loaded from the ELF: every byte of memory arrives
in UDP frames.

What the ROM model does, in order:

1. Holds core 0 and leaves cores 1-5 in reset.
2. Resets and brings up the MAC port the BOOTMODE pins chose, and posts a ten-buffer receive
   ring. The reset is why the announcement matters: a frame that arrived before it is gone with
   the rest of the MAC's state.
3. Sends one BOOTP-shaped Ethernet-ready announcement, naming itself by the MAC address fused
   into the MAC ID words at `02A8 0700h` (`--mac-id` supplies the fuse value, since no public one
   exists). It is sent once and never retransmitted, and nothing in this protocol is acknowledged.
4. Accepts UDP frames on the boot port (`--boot-udp-port`, default 9), checking each as the
   manual specifies: MAC header (DIX, or 802.3 with SNAP/LLC, with or without a VLAN tag), IPv4,
   UDP ports and checksum, then the `0x544B` magic, the opcode, and a sequence number that must
   not skip.
5. Hands each payload to boot-table processing as it arrives — `BootStream` in `src/boot.rs`
   processes the records across fragment boundaries, since no record is guaranteed to fit inside
   one frame.
6. On the terminating zero count, clears the receive channel's head descriptor pointer and
   branches core 0 to the entry point the table named.

One deliberate departure from the letter of §4.3.5, forced by the device model: TI's ROM keeps
its ten 1600-byte packet buffers in L1D at `00F0 0000h`, but no DMA master in this model can
reach a megamodule's *local* L1D window — [SPRS612G](../reference/sprs612g.pdf) Table 2-2 marks
it "DATA SPACE ON DMA" — so the ring and its buffers live in the top of core 0's L2, addressed
through core 0's global alias so the MAC and the boot code name the same bytes. That is inside
the L2 region §4.1 already reserves for the boot code.

### The host side

`tests/tools/emac_boot.py` waits for the announcement, turns each ELF's load segments into a boot
table addressed to the right core, and sends it. The invocation `tests/test_netboot.py` uses:

```console
$ python3 tests/tools/emac_boot.py --socket host.sock --peer emu.sock --json \
      --core 0:image.out --core 1:image.out &
$ c64xemu run image.out --device c6472 --boot-mode 9 \
      --net-unix emu.sock --net-peer host.sock \
      --max-cycles 100000000 --state-out state.json
```

Order matters, and the test enforces it: the sender must bind first, because the announcement is
sent once a few cycles into the boot and a host that is not listening yet has missed it.

Useful sender options, all from `tests/tools/emac_boot.py`: `--entry` overrides the boot table's
entry point, `--release` sets the BOOT_COMPLETE_STAT value written as a section and
`--no-release` omits that section entirely, `--dest-port` (default 9) and `--src-port` move the
UDP ports, `--dst-mac`/`--src-mac`/`--src-ip`/`--dst-ip` set the addresses, `--payload` sets the
bytes per frame (default 1024) and `--gap` the delay between frames.

On the emulator side `--net-port` chooses which MAC receives frames from the backend; by default
it follows the port an Ethernet boot was strapped to.
